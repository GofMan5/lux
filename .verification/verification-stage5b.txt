2. Windows pipe-wait empirical finding
--------------------------------------
Probe program (temp module outside the repo, x/sys v0.35.0,
WaitForSingleObject on an os.Pipe read handle, 200 ms wait):
- empty pipe, writer open: result=0x102 WAIT_TIMEOUT, err=nil, wall 210.1 ms
- pipe with one pending write ("hi"): result=0x102 WAIT_TIMEOUT, err=nil,
  wall 211.5 ms
Consequences, folded into the design:
- WaitForSingleObject never reports failure on pipe handles (no WAIT_FAILED
  path to handle).
- Pipe data NEVER signals the wait: the fast answering path is unreachable
  on Windows pipe input. Production console handles (CONIN$) DO signal, so
  real terminals are unaffected; a pipe-backed stdin on Windows degrades to
  the bounded silent wait (~155 ms measured), never a hang.
- Reply-delivery negotiate tests therefore skip on Windows; timeout/bounded
  paths run everywhere.

5. Known divergences (deliberate)
----------------------------------
- DA1 replies are consumed only in the DEC-private shape ESC [ ? <digits> c
  with a non-empty numeric body — the shape real terminals send. A bare
  CSI-c (no '?') or an empty body is replayed as input rather than treated
  as an answer. A false DA1-positive from keystroke noise would be worse
  (answered=true would veto the probe from real replies). Pinned by
  TestParseProbeReply rows.
- negotiate over a Windows pipe stdin degrades to the bounded silent wait
  (section 2). Not reachable in production (console handles), safe
  everywhere.

7. Round-2 adversarial review (fresh subagent, pre-fix tree)
-----------------------------------------------------------
Verdict: 0 BUG, 1 RISK-high, 1 RISK, 1 RISK-low, 2 NIT. Findings and
disposition (all fixed in the working tree, pinned by tests):
- A (RISK-high) reportEnd window 32 < real DA1: Windows Terminal answers
  DA1 with a 39-byte report (ESC [ ? 61;4;6;7;14;21;22;23;24;28;32;42;52 c,
  clipboard 52; 36 bytes without). The 32-byte scan window rejected it:
  guaranteed full-timeout stall plus a phantom KeyUnknown replay per WT
  launch. Fix: loop bound 32 -> maxSequence (128, shared with parser.go).
  Pinned by TestParseProbeReply "Windows Terminal DA1 answer" (39-byte
  literal -> answered, empty leftover), the full-negotiation row, and
  TestReportEnd window rows moved to index 127/128 plus the WT literal
  (final byte at index 38).
- B (RISK) resize during the probe window was invisible: watchers start
  only after the probe (Unix has no SIGWINCH registered yet, the Windows
  poller baselines after the probe). Fix: Open snapshots the size before
  the probe and, after b.events exists, replays event.ResizeTo when the
  size differs — the app's first layout sees the real terminal size. The
  synthesized event rides the 64-slot channel before any reader exists;
  NextEvent drains it first.
- C (RISK-low) probeRequest comment claimed DECRQM on DECSTBM; DECSTBM is
  a CSI, not a DECRQM-queryable mode. Fix: comments now state DECOM is the
  proxy for scroll regions and why the proxy is sound (the backend never
  sets DECOM; DECSTBM works with DECOM permanently reset).
- D (NIT) invalid LUX_TUI_PROBE_TIMEOUT values fell back to the default
  silently. Fix: one stderr notice (negotiation runs before the alternate
  screen is entered, so the notice cannot disturb a frame) + doc comment.
  Behavior of TestProbeTimeoutConfigured unchanged.
- E (NIT) status 4 (permanently reset) read as supported for mode 2026,
  where the set-mode wrapper would be a permanent no-op. Fix:
  featureFromStatus is mode-aware — status 4 rejects mode 2026, keeps
  supporting mode 6 (DECSTBM still works with DECOM reset). Pinned by
  new rows: sync status 3 -> supported, status 4 -> rejected.
Verified-correct in the same verdict (no action): DECRPM arg order,
byte-order preservation, maxProbeStream bound, bounded leak failure mode,
probe placement.
Re-run gates after the fixes: gofmt, vet, go test -count=1 ./...

10. Round-3 adversarial review (post-commit tree: bcdd046 + 5f3e52f + cd21821)
-------------------------------------------------------------------------
Verdict: 0 BUG, 1 RISK, 1 NIT. Findings and disposition (fix-forward
commit, pinned by tests):
- RISK 1 (confirmed by empirical probe, not just review): Windows
  terminalSize = term.GetSize = GetConsoleScreenBufferInfo on the fd.
  The console splits handles by direction — the screen-buffer query needs
  an OUTPUT handle; on the console input handle (CONIN$) it fails with
  ERROR_INVALID_HANDLE (6); on CONOUT$ it succeeds. The backend holds the
  input side everywhere it asks: terminalSize(b.input) in the probe
  snapshot/replay (B above) and in resizeWatcher.start's baseline/poll.
  So the probe-window replay was dead code on Windows, and the Windows
  resize poller NEVER delivered a resize event (pre-existing, not a
  regression vs HEAD — hence RISK, not BUG; Size() worked because it
  prefers the output handle). Fix: Windows terminalSize now falls back to
  opening CONOUT$ and querying it when the given handle's query fails.
  One change revives the poller, the probe snapshot/replay, and Size()
  with redirected stdout on a console. Unix terminalSize (TIOCGWINSZ on
  the input fd) is untouched — same tty, no redirected-stdout regression.
  Pinned by TestTerminalSizeAnswersThroughInputHandle (opens CONIN$, the
  exact dead handle, asserts a positive size; ran live on this console:
  PASS — it fails without the fallback). The poller call path is the same
  terminalSize, three lines of glue around it.
- B-pin gap (self-found, closed here): the round-2 B fix had no test that
  fails if the pre/post comparison in Open is mutated. Fix: the decision
  is extracted into pure resizeDuringProbe(sizeKnown, pre, post, postErr)
  and table-tested by TestResizeDuringProbe (5 rows: unknown pre size
  quiet, failed post query quiet, unchanged quiet, width change, height
  change — asserting Kind/Width/Height of the synthesized event).
- NIT 1 (documented, not fixed): a probe reply split exactly at the
  deadline (head delivered, tail >35 ms later on a slow ssh) is returned
  unclassified — leftover prefill replays the head, the parser shows the
  leading ESC as one KeyEscape plus literal runes. Cosmetic, once per
  startup at worst, lossless-replay invariant intact; documented in the
  negotiate doc comment as the honest price of a bounded wait.
- The reviewer's re-verification of round-2 fixes A-E and the two
  documented divergences (CONIN$ signaling for reply-delivery tests, DECOM
  proxy) came back clean, as did build/vet/test on the committed snapshot.
Gates re-run on the fix-forward tree: gofmt clean, vet clean, full
