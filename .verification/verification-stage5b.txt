2. Windows pipe-wait empirical finding
--------------------------------------
Probe program (temp module outside the repo, x/sys v0.35.0,
WaitForSingleObject on an os.Pipe read handle, 200 ms wait):
- empty pipe, writer open: result=0x102 WAIT_TIMEOUT, err=nil, wall 210.1 ms
- pipe with one pending write ("hi"): result=0x102 WAIT_TIMEOUT, err=nil,
  wall 211.5 ms
Consequences, folded into the design:
- WaitForSingleObject never reports failure on pipe handles (no WAIT_FAILED
  path to handle).
- Pipe data NEVER signals the wait: the fast answering path is unreachable
  on Windows pipe input. Production console handles (CONIN$) DO signal, so
  real terminals are unaffected; a pipe-backed stdin on Windows degrades to
  the bounded silent wait (~155 ms measured), never a hang.
- Reply-delivery negotiate tests therefore skip on Windows; timeout/bounded
  paths run everywhere.

5. Known divergences (deliberate)
----------------------------------
- DA1 replies are consumed only in the DEC-private shape ESC [ ? <digits> c
  with a non-empty numeric body — the shape real terminals send. A bare
  CSI-c (no '?') or an empty body is replayed as input rather than treated
  as an answer. A false DA1-positive from keystroke noise would be worse
  (answered=true would veto the probe from real replies). Pinned by
  TestParseProbeReply rows.
- negotiate over a Windows pipe stdin degrades to the bounded silent wait
  (section 2). Not reachable in production (console handles), safe
  everywhere.

Two independent reviewers: 52fee989 (verdict below, statically traced,

52fee989 verdict: 0 BUG, 2 RISK, 3 NIT. Findings and disposition (all
fix-forward, never amend):
- RISK 2 (fixed): a resize delivered while the app is still draining a
  64-deep event queue was silently DROPPED and never retried — the
  watchers' send was non-blocking into the shared queue, the Windows
  poller had already advanced its size baseline past the change, and
  Unix had already consumed the SIGWINCH. Worst case is a paste plus a
  resize: the layout stays stale until the NEXT size change. Fix: the
  watchers now deliver into a dedicated one-slot last-wins channel.
  deliverResize(slot, resize) tries a plain send; if the slot holds a
  stale size it drains it and retries, so the newest size is delayed by
  queue depth, never lost. NextEvent polls the resize slot with
  priority over the shared queue (a resize carries the newest terminal
  truth and would otherwise sit behind up to 64 buffered keys), then
  selects on both channels; the shared post-processing (closed check,
  consecutive-resize coalescing, zero-At default, Error kind) moved into
  deliverEvent so both paths share one implementation. Pinned by
  TestDeliverResizeIsLastWins (empty-slot and occupied-slot rows) and
  TestNextEventDeliversResizeBehindFullQueue (64 queued keys, resize
  delivered first, keys not displaced after).
- NIT 1 (fixed): a resize landing in the microseconds between Open's
  post-probe snapshot and the watcher registration was lost on both
  platforms (Unix: SIGWINCH before signal.Notify; Windows: poller
  baseline already reads the new size, no diff, no event). Fix: the
  watcher now starts BEFORE the post-probe snapshot, and the replay
  offers its event into the resize slot as a plain non-blocking send —
  the watcher's report is authoritative and a replay never displaces
  it; equal sizes coalesce in NextEvent. No test: the window is real
  microseconds; the ordering is structural.
- NIT 3 (fixed): Present acquired the write slot with a plain blocking
  send — a second Present parked behind a writer stuck in one long
  Write call forever, the exact hang Close avoids with its bounded
  restoreGrace acquire. Fix: the acquire now selects on ctx.Done() and
  returns ctx.Err() without touching the slot. Pinned by
  TestPresentAbandonsSlotWaitWhenContextDone (slot deliberately held,
  Present bails on a 50 ms deadline; with the old code it parks to the
  10 s hang timeout and fails).
- RISK 1 (fixed as documentation): the defaultProbeTimeout comment
  claimed late reports are "dropped on purpose". They are not: a report
  arriving after the deadline is fully read by readLoop and parses as a
  complete CSI with an unknown final ('c' for DA1, '$y' for DECRPM), so
  the app sees 1–3 phantom KeyUnknown events — on any link with RTT
  beyond the 150 ms budget, every launch. Filtering report-shaped
  sequences at readLoop would also eat pasted input that merely looks
  like a report, so the correct fix is the truth: the comment now
  states the phantom-key cost and points slow links at
  LUX_TUI_PROBE_TIMEOUT. Distinct from the torn-report case already
  documented at the negotiate loop (report split exactly at the
  deadline replays as a leading ESC plus literal runes).
- NIT 2 (documented as deliberate): reportEnd's scan window is one byte
  stricter than the parser's maxSequence (i < vs <=). The comment
  previously claimed the two "match". The strictness is kept on
  purpose: a report that long is pathological (real DA1s run 36-39
  bytes), and leaving it in leftover surfaces it as one unknown key
  instead of classifying a shape that long; the body validators and
  maxProbeStream remain the real guards.
- Reviewer's VERIFIED-CORRECT list (negotiation loop and deadline
  unwind, maxProbeStream cap, parseProbeReply grammar and leftover
  replay, env maps, featureFromStatus, Open ordering and unwind, Close
  bounded restore, NextEvent dedupe, Present slot serialization and
  model discard, readLoop prefill and escape-delay, encoder sync
  gating, first-frame nil guards, detectCapabilities, existing pins)
  accepted as given.
