Policy semantics (pinned by tests, traced to code):
  - zero policy = byte-identical legacy behavior: active() is false, so no
    policy table is ever consulted; TestWidthPolicyZeroMatchesLegacy pins
    the fast path including an inactive AmbiguousWidth=3
  - AmbiguousWidth==2 (any other value, incl. 0/3/-5, behaves as 1): a
    width==1 cluster whose BASE rune is EAW-A is bumped to 2 (adjust runs
    after terminalWidthOf, before the VS16 handling and narrow logic).
    e+combining is judged by the base (Latin e is not ambiguous -> stays 1)
  - VS16Blind: exactly one trailing U+FE0F is stripped, then the remainder
    is re-measured through the same pipeline (recursion, so "wide base +
    FE0F + more" still works); U+FE0E is never stripped; a lone FE0F is
    width 0; double FE0F strips one
  - NarrowEmoji: a width==2 cluster with an Emoji_Presentation base rune,
    OR any cluster containing FE0F, is narrowed to 1; undecodable base
    falls through; CJK wide ideographs never narrow (they are not
    Emoji_Presentation)
  - policy order is fixed: VS16-blind strip BEFORE adjust, so
    VS16Blind+NarrowEmoji compose (stripped "❤" -> narrow-blind terminal
    sees text base -> 1 via either knob); TestWidthPolicyKnobsCombine
    covers the 2x2 knob matrix
  - lux.WithWidthPolicy validates AmbiguousWidth in {1,2} at option
    evaluation time and returns an error before the backend opens
  - coherence: the policy rides the canvas (Canvas/Subview/Clip), so Text
    advance, TextWidth, Button/Modal/ListBox truncation, TextInput caret,
    horizontal scrolling and mouse click/drag mapping all see the same
    cells; the app-level test pins a presented frame's wide cell +
    continuation, and the ui tests pin byteAtCell semantics (cell-x >=
    (cells+1)/2 lands after the grapheme)
