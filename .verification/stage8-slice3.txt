API (verified by test, not by inspection):
  - TabsState zero value selects tab 0 with offset 0, ready. Tabs(id,
    canvas, rect, state, labels, style) — labels are APP-OWNED, the widget
    never stores them; the same slot math (label width + 1 padding cell per
    side) drives drawing AND tabAt pointer hits, so a press on slot x
    selects that tab directly on the closing release (changed=true,
    activated=true) while a press on the SELECTED tab reports
    changed=false, activated=true (an honest press still "activates" a
    strip that has nothing to change).
  - Navigation selects like a radio: Left/Right/Home/End (scroll keys)
    and wheel steps move the choice; page keys and vertical keys are
    inert; key releases are inert. applyOffset (keepTabVisible) advances
    the strip offset minimally so the selected tab's whole slot stays
    visible — ONLY for Kind==Scroll (a pointer pick that jumps to an
    out-of-view tab does NOT scroll the strip, matching radio row picks),
    and a tab wider than the whole strip clips from the strip's left edge
    instead of vanishing (width<=0 guards in the slot walk).
  - The strip region is Focusable|Scrollable|Activatable, one row tall,
    so Tab reaches it, horizontal arrows scroll it (see the routing fix),
    and completed clicks select. Mouse press on the strip routes as
    Scroll with region-local coordinates (strip strip-local X), release
    captures the same region and maps the point through tabAt.
  - GaugeState{Value, Max} is display-only: Fraction() = Value/Max
    clamped to [0,1], Max<=0 becomes 1, NaN never arises (guarded). The
    bar is full cells "█", a half cell "▌" when the remainder is >= 0.5 of
    a cell, then light-shade track "░" to the width; H>1 repeats the same
    row. NO region, NO routing, NO focus: "seek" would need its own press
    contract and is not claimed. Nil state draws nothing.
  - SpinnerState{Started} is display-only: phase =
    int(Age(now)/FrameDuration) % len(Frames), a PURE function of
    absolute time, so 10 FPS and 240 FPS presenters draw the same glyph at
    the same wall-clock instant; the app passes `now`, which makes drawing
    deterministic for tests and replay. Presets: SpinnerASCII "|/-\"
    (4-phase, 100ms default), SpinnerBraille (10-phase), SpinnerArc
    "◐◓◑◒" (4-phase; frame 1 is "◓"). Zero Started or a nil state paints
    the resting first frame. FrameDuration<=0 becomes 100ms. NO region,
    NO routing, NO focus; frame SCHEDULING stays the runtime pacer's job
    (the showcase's continuous RequestFrame drives its live demo).

Routing fix (ui/context.go, pinned by
TestContextHorizontalArrowsServeFocusedRegion):
  - scrollKey now also answers KeyLeft/KeyRight: horizontal arrows are
    navigation keys for horizontal widgets (tab strips), like up/down for
    vertical lists. scrollKeyUp stays vertical-only, so horizontal arrows
    NEVER bubble through an enclosing vertical viewport — the focused
    region always receives them as Scroll actions. KeyLeft AND KeyRight on
    a focused strip inside a 12x1 viewport viewport both route to the
    strip (Kind==Scroll, region-local point), asserted by test.
  - Behavior change: non-priority ScopeApp shortcuts bound to bare
    Left/Right are now shadowed by any focused scrollable region. No
    shipped example binds one; catalog and showcase unaffected (verified
    by their full e2e passes).
  - Found live: the widgets-catalog e2e timed out pressing KeyRight on
    the page tabs — the router dropped the key, the app never advanced,
    the test never saw the state. This is exactly the class of bug the
    e2e catalog exists to catch.
