Stage 6, slice 5 — keyboard truth: synchronized output enabled by the probe — local verification, 2026-10-07
=============================================================================================================

Scope (ROADMAP.md, stage 6 item 5): synchronized output stops being
env-var-only opt-in and becomes probe-driven — a positive DECRPM 2026
answer enables the frame wrapper, a rejection disables it, and
LUX_TUI_SYNC_OUTPUT remains an override in both directions (force-on /
force-off). Landed as one commit:

  (this commit) feat: enable synchronized output by probe
               internal/terminal: syncOutputMode tri-state (auto/on/off) +
               syncOutputConfigured (empty|auto|default -> auto,
               1|true|yes|on -> on, 0|false|no|off -> off, anything else ->
               auto after a one-line stderr notice, the probeTimeoutConfigured
               pattern); detectCapabilities now claims the flag only for a
               forced-on override (with negotiation disabled nothing else
               could enable it); applyProbeFeatures gains the mode argument
               and drives SynchronizedOutput both ways — supported sets it,
               rejected clears it, silence keeps the base; the override
               replaces the verdict entirely in either direction. Present
               and the encoder are untouched: they already wrap any frame
               when the flag is set, and already never wrap when it is not.

Design invariants (all preserved):
  - the safe default: an unconfirmed terminal (silent probe, negotiation
    disabled) never receives \x1b[?2026h/l; auto starts from false.
  - the override wins over the report in BOTH directions — it exists for
    a terminal whose report lies; force-on beats a veto, force-off beats
    a recognized answer.
  - the plain profile never sees the wrapper (plain snapshots are
    newline-delimited, no mode-set involved).
  - statuses 1/2/3 (set/reset/permanently set) all count as "recognized":
    the backend wraps each frame explicitly, so the reported current state
    does not matter; 0 (unrecognized) and 4 (permanently reset) are
    rejections — with 4 the set-mode wrapper would be a permanent no-op
    and the frames would stream unsynchronized anyway (unchanged logic in
    featureFromStatus).
